# 摘要

本文完成了三项工作。其一，选取 etcd 作为类 Chubby 的开源项目，基于其源码分析了系统架构以及选举、日志复制、持久化、租约与分布式锁等关键代码。其二，在不调用任何现成共识库的前提下，以约 1,800 行 Python 代码实现了 Paxos 协议原型，包含 Proposer、Acceptor、Learner、Listener 四种角色，支持 Basic Paxos、Multi-Paxos 与 Fast Paxos 三种提案机制，并实现了批处理与心跳选主两项优化；节点间采用 TCP 自定义二进制报文通信，Acceptor 状态在应答前持久化。其三，围绕节点规模、并发度、网络时延、丢包率、持久化方式与节点故障开展了 11 组共 382 次实验。实验表明：Multi-Paxos 在全部条件下无提案冲突，时延稳定在 1 至 2 个 RTT；Basic Paxos 在三个及以上 Proposer 无退避竞争同一实例时出现活锁；Fast Paxos 的平均时延在冲突率超过约 18%（3 节点）或 27%（4 节点）后高于 Multi-Paxos；Leader 故障恢复时间约为选举超时的 1.33 倍；全部实验累计比对约 120.7 万个实例，未出现不同 Learner 学到不同值的情况。受条件所限，实验在单机多进程环境中完成，未使用 Docker 或虚拟机，详见第二章。

# 二、实验环境

## 2.1 部署方式

作业要求使用 3 至 4 台 Ubuntu 虚拟机或 Docker 容器。完成本作业所用的计算机未安装 Docker、WSL 及任何虚拟机软件，因此实验采用单机多进程方式进行：每个 Paxos 节点为一个独立的操作系统进程，各自监听回环地址上的固定端口，节点之间通过真实的 TCP 连接通信；时延、丢包与网络分区由节点内的应用层注入模块产生；节点故障通过强制终止进程模拟，重启后由持久化日志恢复。协议代码仅依赖 Python 标准库，与部署平台无关。为便于在多机环境复现，工程中提供了 Docker 镜像定义、固定 IP 的 Docker Compose 配置（4 个投票节点与 1 个 Listener）、基于 tc netem 的故障注入脚本以及虚拟机启动脚本；上述部署文件仅通过了语法检查，未在真实容器环境中运行。

实验主机为 Intel Core i9-13900HX（32 逻辑核）、16 GB 内存、Windows 11，运行环境为 Python 3.10.14。数据盘为 USB 移动固态硬盘，单次 fsync 耗时约 2 ms。每次实验均配置 3 至 5 个投票节点与 1 个 Listener。默认参数为：心跳间隔 50 ms，选举超时基数 300 ms（实际超时在一至两倍基数之间随机），重试超时为 max(60, 3·RTT+40) ms，冲突退避基数 5 ms，批大小为 1，除持久化实验外关闭 fsync。

## 2.2 故障注入与度量方法

时延注入的方式为：节点间报文在发送端按链路排队，延迟 RTT/2 后写入套接字。每次实验开始前实测链路往返时延，目标值 1、10、50、100 ms 对应的实测值约为 1.2、10.2、50.2、100.2 ms；不注入时延时实测约为 0.2 ms。丢包注入的方式为：节点间报文以给定概率被直接丢弃且不重传，丢失后只能依靠协议自身的超时重试恢复。该模型与内核层的 tc netem 存在差别：后者作用于 TCP 之下，丢失的数据段由内核重传，应用层观察到的是连接停顿而非报文消失。因此本文关于丢包的结论仅适用于报文级丢失模型。网络分区通过在收发两端丢弃分区两侧之间的全部报文实现。

负载分为两类。闭环负载由若干客户端各自串行地发送请求并等待响应，用于测量吞吐上限与并发的影响；开环负载按泊松过程以固定速率产生请求，用于在相同到达率下比较时延。客户端均匀连接至各投票节点。主要度量指标的定义为：吞吐指统计窗口内成功请求数与窗口时长之比；时延指客户端自发出请求至收到已选定响应的时间；消息数指每条成功命令对应的节点间报文数，含心跳与重传；冲突率在 Basic Paxos 中指因提案编号被抢占而失败的轮次占全部轮次之比，在 Fast Paxos 中指未能取得所选实例而需重新提案的直接提案占比；不可用窗口指故障注入后相邻两次成功完成之间的最长间隔；分歧实例数指实验结束后逐实例比对全部节点所学到的值时，取值不一致的实例个数。除恢复时间实验外，每个数据点仅运行一次，未给出置信区间。

# 三、开源项目架构分析

## 3.1 项目选取与总体架构

Chubby 是 Google 的粗粒度锁服务，以 Paxos 将一个小型文件系统复制到多个副本，对外提供锁、会话、事件通知与小文件存储。本文选取 etcd 作为分析对象，原因在于其功能与 Chubby 逐项对应（键值存储对应小文件，Lease 对应会话，Watch 对应事件，并发库中的 Mutex 对应锁），且其共识层是独立的 Raft 库，便于与本文实现的 Paxos 对照。分析所依据的源码为 etcd-io/etcd 提交 76d58e32b30d 与 etcd-io/raft 提交 1c0011d2c6b7。不含测试代码，Raft 库约 1.16 万行，服务端核心约 2.58 万行。更为详细的分析见随附文档 `docs/etcd架构分析.md`。

etcd 是典型的复制状态机。写请求首先被编码为日志条目，经 Raft 在多数派节点上持久化后提交，再由各节点按相同顺序应用到本地存储。系统自上而下分为四层：gRPC 接口层负责请求校验与配额控制；EtcdServer 负责将请求提交给 Raft 并等待应用结果；共识层为不执行任何 I/O 的纯状态机，通过 Step 接收消息与时钟信号，通过 Ready 输出待持久化的条目、待发送的消息与已提交的条目；存储层由预写日志（WAL）与基于 bbolt 的多版本键值存储构成，前者保存尚未应用的日志，后者保存已应用的状态。共识逻辑与网络、磁盘相分离，是该架构最主要的特点。

## 3.2 关键代码分析

选举逻辑位于 `raft/raft.go`。Follower 在 `tickElection()` 中累计计时，超过随机化的选举超时后进入 `campaign()`，向其他节点发送携带本地最后一条日志的任期与索引的投票请求。投票方在 `Step()` 中判定：仅当本任期尚未投票且候选者的日志不落后于自身时才予以同意，后一条件由 `raftLog.isUpToDate()` 实现。该约束保证当选者拥有全部已提交条目，因而新 Leader 无需向其他节点索取日志；Paxos 则允许任意节点当选，而由 Phase 1 的应答带回各 Acceptor 已接受的值。此外，etcd 默认启用 PreVote 与 CheckQuorum：前者要求候选者在真正递增任期之前先行试探能否获得多数派支持，后者使在一个选举超时内收到过 Leader 心跳的节点忽略投票请求，二者共同避免被隔离的节点在恢复连接后以较高任期干扰正常的 Leader。

日志复制方面，Leader 在 `stepLeader()` 中将提案追加至本地日志并向各 Follower 广播；Follower 在 `handleAppendEntries()` 中依据前一条目的任期与索引进行一致性检查。提交位置由 `quorum/majority.go` 中的 `CommittedIndex()` 计算：将各投票节点已确认的索引排序，取其中被多数派确认的最大者。由于日志连续，Raft 只需为每个 Follower 维护一个确认位置即可确定整段日志的提交点，而 Paxos 的各实例需分别计票。

持久化顺序由 `etcdserver/raft.go` 中的 `raftNode.start()` 决定。对每个 Ready，Follower 必须先将条目与硬状态写入 WAL，然后才能发送应答消息；Leader 则可以先发送日志追加消息再写本地磁盘，因为其自身的确认仅在本地落盘后才计入多数派。是否需要同步刷盘由 `raft.MustSync()` 判定，条件为存在新的日志条目，或任期、投票对象发生变化，这三项恰与 Paxos 中的 accepted_value 与 promised_id 相对应。本文实现中 Acceptor 先持久化后应答的回调结构即参照了这一设计。

租约与锁是 etcd 与 Chubby 最为接近的部分。`lease/lessor.go` 中仅 Leader 上的 lessor 负责检测租约到期，到期后由服务端发起撤销提案并经 Raft 提交，使各副本在同一日志位置删除附着于该租约的键；Leader 切换时，新 Leader 调用 `Promote()` 将全部租约延长一个选举超时，其思想与 Chubby 在主节点切换时设置宽限期一致。分布式锁由 `client/v3/concurrency/mutex.go` 实现：客户端在一个事务中以创建版本号为零作为条件写入绑定自身租约的键，并读取同一前缀下创建版本号最小的键；若该键属于自己则获得锁，否则仅监视排在自己之前的键被删除。锁的排队顺序由共识日志决定，持有者失效时由租约到期自动释放。

## 3.3 与 Chubby 及本文实现的比较

| 比较项 | Chubby | etcd | 本文原型 |
|---|---|---|---|
| 共识协议 | Multi-Paxos | Raft | Basic、Multi、Fast Paxos |
| Leader 产生方式 | 主节点租约与 Paxos 选主 | 随机超时选举，日志最新者当选，PreVote 与 CheckQuorum | 心跳超时后发起范围 Prepare，任意节点可当选 |
| 新 Leader 补齐日志 | Phase 1 收集已接受值 | 选举约束保证，无需补齐 | Promise 带回已接受值并重新提案 |
| 持久化规则 | 先写日志后应答 | 条目、任期、投票变化时同步刷盘 | Acceptor 先写 WAL 后应答，组提交 |
| 会话与锁 | 会话、锁与序号 | Lease、事务与创建版本号 | 未实现 |
| 成员变更与日志压缩 | 支持 | 联合共识、快照与压缩 | 未实现 |

上表表明，本文原型与工业系统的差距主要在于成员变更、日志压缩与快照、线性一致读以及客户端会话。这些功能不属于共识算法本身，却构成了 etcd 服务端代码的主体。

# 四、Paxos 协议实现

## 4.1 总体设计与报文格式

原型由五个模块组成：`wire.py` 负责报文编解码与提案编号，`storage.py` 实现 Acceptor 的预写日志，`net.py` 负责 TCP 连接管理与故障注入，`node.py` 实现各角色与三种提案机制，`client.py` 提供客户端与负载发生器。每个节点进程同时承担 Proposer、Acceptor 与 Learner 三种角色；Listener 节点仅运行 Learner，不参与投票。系统将 Paxos 组织为多实例日志，各实例独立选定一个值，值为一批客户端命令，所有节点按实例号顺序将已选定的值应用到状态机。三种提案机制共用同一套 Acceptor 与 Learner，区别仅在 Proposer 一侧。

节点间采用 TCP 长连接，报文由 40 字节定长头部与变长负载组成，各字段均为网络字节序：

```
 0      2     3     4      6       8          16         24         32      36     40
 +------+-----+-----+------+-------+----------+----------+----------+-------+------+---------
 | 'PX' | ver | typ | src  | flags |   slot   |  ballot  |   aux    |  len  | crc  | payload
 +------+-----+-----+------+-------+----------+----------+----------+-------+------+---------
```

其中 slot 为实例号，ballot 为提案编号，crc 为负载的 CRC32 校验值。报文共 17 种，主要包括 PREPARE、PROMISE、ACCEPT、ACCEPTED、NACK、LEARN、HEARTBEAT、FAST_PROPOSE、FORWARD 与 LEARN_REQ。提案编号为 64 位整数，由轮次、节点号与一位轮次类型依次拼接而成，按数值比较即得到全序，且全局唯一；Proposer 每发起一轮即递增轮次，并在收到更高编号时将本地轮次更新至该值，从而保证编号单调递增。

## 4.2 基本协议

Acceptor 为每个实例维护 promised_id、accepted_id 与 accepted_value，并维护一个对全部实例生效的范围承诺编号。收到 PREPARE 时，若其编号高于已承诺编号，则记录承诺并返回该实例已接受的编号与值，否则返回 NACK 并附带已承诺的编号；收到 ACCEPT 时，若其编号不低于已承诺编号，则接受该值并返回 ACCEPTED，否则返回 NACK。

持久化由预写日志实现。Acceptor 的每次承诺与接受均作为一条带 CRC 校验的记录追加写入日志文件，应答报文在记录写入完成后才发送；启用 fsync 时，事件循环一轮内积累的全部记录合并为一次写入与一次同步刷盘，以摊薄刷盘开销。节点启动时顺序重放日志以恢复状态，遇到长度不足或校验失败的尾部记录即予以截断。图 4-1 为运行中节点的日志文件内容。经验证，3 节点集群在启用 fsync 的条件下提交 2,130 条命令后被同时强制终止，重启后各节点分别由日志重放 2,131 至 2,133 条记录，新 Leader 通过 Phase 1 取回各 Acceptor 已接受的值并重新提案，全部实例得以恢复。

![图 4-1 Acceptor 持久化日志：解码后可见范围承诺的 promised_id 以及各实例的 accepted_id 与 accepted_value，下部为文件起始处的原始字节](screenshots/03_wal.png)

Basic Paxos 模式下，任一节点收到客户端命令后均以 Proposer 身份对一个空闲实例执行完整的两阶段流程：Phase 1 向全部 Acceptor 发送 PREPARE 并等待多数派 PROMISE，若应答中包含已接受的值，则必须改为提出其中编号最高者；Phase 2 发送 ACCEPT 并等待多数派 ACCEPTED；成功后向包括 Listener 在内的全部节点广播 LEARN。任一阶段被拒绝或超时，Proposer 按随机指数退避等待后以更高编号重试；若该实例最终选定的并非自己的命令，则更换实例重新提案。无冲突时每条命令需 4 个消息时延，即 2 个 RTT。Learner 以命令的全局唯一标识去重，并在同一实例学到不同值时记录安全性违例；落后的节点通过 LEARN_REQ 向其他节点请求补发已选定的值。

## 4.3 优化机制

Multi-Paxos 以心跳机制选出稳定的 Leader。投票节点在选举超时内未收到心跳即发起范围 Prepare，以一次 Phase 1 覆盖其后的全部实例；获得多数派承诺后成为 Leader，对应答中出现过已接受值的实例按最高编号者重新提案，其余空缺填入空操作。此后的新实例跳过 Phase 1，直接执行 Phase 2。非 Leader 节点将客户端命令转发给 Leader，因此在 Leader 上提交需 1 个 RTT，在其他节点上提交需 2 个 RTT。Leader 可同时推进多个实例，并在提案被更高编号拒绝或收到更高编号的心跳时退位。批处理在此基础上将多条排队的命令合并至同一实例，共享一轮报文交互与一次落盘。

Fast Paxos 允许 Proposer 绕过 Leader 直接向 Acceptor 提案。设节点数为 n，经典多数派 qc 取 ⌊n/2⌋+1，快速多数派 qf 取满足 qc+2·qf>2n 的最小值，n 为 3、4、5 时 qf 分别为 3、3、4。协调者以快速轮编号完成范围 Prepare 后通过心跳下发许可，Acceptor 在该轮的每个实例上仅接受最先到达的值，并将结果同时告知提案者与协调者；提案者收到 qf 个接受其值的应答即视为选定，全程为 2 个消息时延。多个提案者的值在同一实例上相遇时发生冲突，由协调者进行恢复：设已上报的 Acceptor 集合为 Q，若某值 v 满足 |Q|−cnt(v) ≤ n−qf，即该值仍可能已被某个快速多数派选定，则必须选取 v，否则可任选其一，随后以紧邻的经典轮编号发送 ACCEPT 完成选定。由于 Acceptor 在快速轮中的投票不可更改，且编号编码保证快速轮与其后的经典轮之间不存在其他编号，上述上报可直接充当下一轮的 Phase 1 应答，恢复过程无需额外的 Prepare。

## 4.4 实现过程中发现的问题

实验过程中曾出现 Fast Paxos 模式下集群停止提交的现象。经排查，其原因在于启动阶段多个节点同时竞选，落选者的范围 Prepare 使部分 Acceptor 承诺了高于当选者的编号。在 Multi-Paxos 中，Leader 的 ACCEPT 被这些 Acceptor 拒绝后会退位并以更高编号重新竞选，问题得以自行消除；而 Fast Paxos 的直接提案不经过协调者，Acceptor 的拒绝无人处理，受影响的节点不再接受直接提案。修复方法为：Acceptor 收到编号低于自身承诺的心跳时返回 NACK，促使 Leader 退位重选。该缺陷只影响活性，停止提交期间一致性检验未发现违例。修复后重新执行了全部实验，本文数据均为修复后的结果。

# 六、临界点分析

## 6.1 3、4、5 节点的多数派与容错能力

n 个节点的经典多数派为 ⌊n/2⌋+1，可容忍 n−(⌊n/2⌋+1) 个节点失效。3、4、5 节点的多数派分别为 2、3、3，可容忍的失效节点数分别为 1、1、2。Fast Paxos 的快速多数派分别为 3、3、4，快速路径可容忍的失效节点数分别为 0、1、1。5.4 节的实验与上述结论一致：3 节点与 4 节点在失效 1 个节点时继续提供服务，失效 2 个节点时不可用；5 节点在失效 2 个节点时继续提供服务，失效 3 个节点时不可用。

## 6.2 4 节点不一定优于 3 节点的原因

对于采用经典多数派的 Basic Paxos 与 Multi-Paxos，4 节点在四个方面不及 3 节点。第一，容错能力未提高，多数派由 2 增至 3，仍仅能容忍 1 个节点失效。第二，不可用概率更高：设各节点独立失效的概率为 q，两种规模均在至少 2 个节点同时失效时不可用，其概率分别约为 3q² 与 6q²。第三，开销更大：Multi-Paxos 每条命令的报文数增加 41%，64 并发下的吞吐降低 13%。第四，对丢包更为敏感：Leader 自身计一票，3 节点时其余 2 个 Acceptor 中有 1 个往返成功即可，4 节点时其余 3 个中需有 2 个成功；单程丢包率为 10% 时，一次往返成功的概率为 0.81，首次发送未能凑足多数派的概率在 3 节点下为 3.6%，在 4 节点下为 9.5%，后者约为前者的 2.6 倍，这与 5.2 节中 4 节点在丢包下吞吐更低的结果相符。

对于 Fast Paxos，结论相反。3 节点的快速多数派为全部节点，任一节点失效或接受了不同的值，快速路径即告失败；4 节点的快速多数派为 3，允许 1 个节点失效或意见不一致。实验中，终止协调者后 4 节点的不可用窗口为 54 ms，3 节点为 427 ms；4 节点的冲突临界点也更高（见 6.5 节）。因此，节点数的选择应结合所采用的多数派类型：经典 Paxos 宜取奇数，Fast Paxos 则在 4 节点时才具备快速路径的容错能力。

## 6.4 Multi-Paxos 的性能优势与 Leader 故障恢复时间

Multi-Paxos 性能较高的原因有三。其一，稳定的 Leader 对其后全部实例仅执行一次 Phase 1，每条命令只需 Phase 2，在 Leader 上提交为 1 个 RTT，报文数约为 Basic Paxos 的一半或更少。其二，实例号由 Leader 统一分配，不存在 Proposer 之间的竞争，全部实验中冲突率为零，P99 与 P50 基本一致。其三，Leader 可并行推进多个实例并进行批处理，吞吐随并发度线性增长，落盘也随之合并，每条命令的刷盘次数为 Basic Paxos 的 29%。

Leader 故障恢复时间由三部分构成：故障检测、选举与补齐。选举超时在 T 至 2T 之间均匀随机，3 节点中 Leader 失效后由两个 Follower 中先超时者发起选举，其期望约为 1.33T，再减去距上一次心跳已过去的时间（平均约 25 ms）；选举与补齐各需 1 个 RTT。据此预测恢复时间约为 1.33T−25 ms+2·RTT。RTT 为 10 ms 时，T 取 150、300、600、1200 ms 的预测值为 195、395、795、1595 ms，表 5-6 中的实测平均值为 203、378、829、1652 ms，二者吻合。因此恢复时间基本由选举超时决定。减小选举超时可缩短恢复时间，但其取值须远大于心跳间隔与 RTT，否则在丢包条件下容易误判；5.2 节中丢包率达到 30% 时即出现了误选举。

临界冲突率在 3 节点下约为 18%，在 4 节点与 5 节点下约为 27% 至 29%，且在两种 RTT 下基本相同，说明该阈值取决于协议结构而非网络条件。对应的负载条件为总到达率与 RTT 之积约为 0.6 至 0.9，即平均每个 RTT 内出现接近一条来自其他 Proposer 的提案。该阈值可用成本模型解释：客户端均匀分布时 Multi-Paxos 的平均时延为 (2n−1)/n 个 RTT，Fast Paxos 无冲突时为 1 个 RTT，一次冲突的额外代价包含失败的直接提案、协调者恢复、退避与重新提案，据交叉点反推约为 3 至 4 个 RTT。4 节点的阈值较高，是因为两个值相遇时仍可能以三比一的票数被直接选定。需要说明的是，上述结论针对平均时延；若以 P99 衡量，冲突率为 1.6% 时 Fast Paxos 已高于 Multi-Paxos。

## 6.6 RTT 与丢包对吞吐的影响界限

在所测范围内（RTT 不超过 100 ms，丢包率不超过 40%）未出现吞吐骤降为零的界限。若以吞吐降至无丢包时的一半作为判据，3 节点 Multi-Paxos 在 RTT 为 1、10、50、100 ms 时的临界丢包率分别为 5%、20%、30%、30%；以降至五分之一为判据，则分别为 10%、40%、高于 40%、高于 40%。决定该界限的是一次丢失的代价即重试超时与正常提交时延之比：RTT 为 1 ms 时重试超时为正常时延的数十倍，RTT 为 100 ms 时仅为两至三倍。这说明重试超时应随 RTT 自适应调整。

就 RTT 本身而言，Multi-Paxos 不存在崩溃点，吞吐与 RTT 成反比，时延稳定在 1 至 2 个 RTT。Basic Paxos 与 Fast Paxos 在并发负载下随 RTT 增大而逐渐恶化，RTT 达到 50 ms 时二者的 P99 分别超过 1 s 与 1.6 s。另一个界限是 Leader 的稳定性：丢包率达到 30% 时开始出现误选举，当丢包率高到选举超时内的心跳可能全部丢失时，集群将陷入反复选举。上述结论限于报文级丢失模型；在 TCP 之下发生丢包的真实环境中，等效的重试代价为 TCP 的重传超时，低 RTT 下的临界丢包率预计更低，本文未作实测。

## 6.7 导致系统不可用的故障节点数

失效节点数达到 n−⌊n/2⌋ 时，剩余节点不足以构成多数派，系统不可用。该数值在 3 节点与 4 节点时为 2，在 5 节点时为 3。实验中自达到该数目起，完成的请求数为零，直至有节点重启；期间提交的请求或超时失败，或在恢复后完成，恢复后各节点状态一致。此外存在三种局部不可用的情形：Leader 单独失效时出现约 1.33 倍选举超时的不可用窗口；被划分至少数派一侧的节点无法提交任何请求；Fast Paxos 在 3 节点失效 1 个或 5 节点失效 2 个时快速路径失效，系统退化为每条命令均经协调者恢复的模式，但仍可用。

## 6.8 安全性是否始终得到保证

在全部 382 次实验累计 1,207,019 个实例的比对中，分歧实例数为零，节点运行期间的违例计数亦为零，其中包括三种机制在 3 节点与 4 节点下的随机故障测试。安全性不依赖时序假设，时延、丢包、分区与宕机仅影响活性。其保证来自三条规则：任意两个多数派相交，Fast Paxos 另需满足 qc+2·qf>2n；Acceptor 不接受编号低于已承诺编号的提案，快速轮中每个实例仅接受一个值，且上述状态在应答前持久化；Proposer 在 Phase 1 中沿用可能已被选定的值。

上述结论有以下限制。第一，测试不能证明正确性，未发现违例不等于不存在可触发违例的场景。第二，实验中的故障为终止进程，操作系统页缓存中的数据不会丢失，因而未能检验关闭 fsync 时整机掉电的后果；在该情形下 Acceptor 可能丢失已应答的承诺，安全性不再成立。第三，仅考虑了崩溃故障，未涉及拜占庭故障与磁盘静默损坏。第四，活性并非始终得到保证，Basic Paxos 存在活锁，实现过程中 Fast Paxos 亦出现过停止提交的缺陷。

# 七、结论与不足

本文分析了 etcd 的架构与关键代码，实现了支持三种提案机制的 Paxos 原型，并通过实验得到以下结论。Multi-Paxos 在各项条件下表现最为稳定，无提案冲突，时延为 1 至 2 个 RTT，吞吐随并发度线性增长，其代价是 Leader 失效时存在约 1.33 倍选举超时的不可用窗口。Basic Paxos 仅适用于单一 Proposer 或并发度极低的场合，三个及以上 Proposer 无退避竞争时出现活锁。Fast Paxos 在冲突率低于约 18%（3 节点）或 27%（4 节点）时平均时延优于 Multi-Paxos，超过后迅速恶化。采用经典多数派时 4 节点在容错、可用性、开销与抗丢包方面均不及 3 节点，而 Fast Paxos 在 4 节点时才具备快速路径的容错能力。选举超时、退避窗口与重试超时三项参数均应随 RTT 自适应设置。

本文存在以下不足。实验在单机多进程与应用层故障注入条件下完成，未使用 Docker 或虚拟机，丢包模型与真实网络不同。除恢复时间实验外各数据点仅运行一次，部分结果在不同次运行间存在波动。原型以单线程 Python 实现，不注入时延时的绝对吞吐不具代表性。成员变更、日志压缩、线性一致读、PreVote 与 Leader 租约等功能尚未实现。
