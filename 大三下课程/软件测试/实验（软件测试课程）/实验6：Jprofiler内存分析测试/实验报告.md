## 一、实验目的

1. 掌握 JProfiler 的安装与配置。
2. 掌握使用 JProfiler 对 Java 程序进行监测，能够：
   - 判断并查找内存泄漏；
   - 判断线程是否阻塞；
   - 分析代码运行效能（CPU 热点）。

## 三、JProfiler 安装与配置

### 3.1 安装 JProfiler 本体

1. 运行已下载的 JProfiler 安装包，按向导完成安装。
2. 首次启动时选择 **Evaluation（评估版）** 或输入 License Key。
3. 记录 JProfiler 安装路径，例如：`C:\Program Files\jprofiler13`（版本号以实际为准）。

**【此处插入截图：JProfiler 安装完成 / 许可证选择界面】**

参考教程：[JProfiler 安装](https://blog.csdn.net/shiyong1949/article/details/52574896)

### 3.2 在 IDEA 中安装 JProfiler 插件

1. 打开 IDEA → **File → Settings → Plugins**。
2. 搜索 **JProfiler Integration**，安装并重启 IDEA。
3. 进入 **File → Settings → Tools → JProfiler → JProfiler**：
   - 勾选 **Integrate JProfiler with IDEA**；
   - **JProfiler executable** 指向本机 `bin\jprofiler.exe`；
   - **JProfiler agent library** 指向 `bin\windows\jprofiler.dll`（64 位系统）。

**【此处插入截图：IDEA 插件安装与 JProfiler 路径配置】**

参考教程：[IDEA 集成 JProfiler 插件](https://blog.csdn.net/chao821/article/details/90340843)

1. 用 IDEA 打开本实验目录。
2. 确认 `src` 为 Sources Root（右键 `src` → Mark Directory as → Sources Root）。
3. 运行配置：
   - **Run → Edit Configurations → + → Application**

## 四、使用 JProfiler 监测与分析

### 4.1 启动监测

### 4.2 内存泄漏查找

#### 4.2.1 操作步骤

1. 在 IDEA 中 Profile 启动 `Main`（参数 `1` 或 `4`）。
2. 在 JProfiler 左侧选择 **Live Memory** 或 **Memory Views → All Objects**。
3. 观察 **Heap Size** 曲线是否持续上升且不回落。
4. 在对象列表中按 **Size** 或 **Instance Count** 排序，查找：
   - `byte[]` 占用显著增大；
   - `com.lab.jprofiler.MemoryLeakDemo$LeakItem` 实例数持续增加。
5. 右键 `LeakItem` → **Show in Heap Walker** → **References** → **Incoming References**，可看到被 `LEAK_CACHE`（`ArrayList`）持有，无法被 GC 回收。

#### 4.2.2 泄漏原因分析

演示代码 `MemoryLeakDemo.java` 中：

```java
private static final List<LeakItem> LEAK_CACHE = new ArrayList<>();
// 循环中不断 add，且从未 remove/clear
LEAK_CACHE.add(new LeakItem(...));
```

每个 `LeakItem` 内含约 1MB 的 `byte[]`，静态集合导致对象生命周期与进程相同，形成典型 **内存泄漏**。

#### 4.2.3 修复建议

- 对缓存设置容量上限（LRU）或定期 `clear()`；
- 避免无界静态集合；
- 使用 WeakReference 或专业缓存库（Caffeine 等）。

### 4.3 线程阻塞判断

#### 4.3.1 操作步骤

1. Profile 启动 `Main`，参数 `2` 或 `4`。
2. 打开 **Threads** 或 **Thread History** 视图。
3. 等待约 3 秒后，查看 `Worker-Thread-1`、`Worker-Thread-2` 状态是否为 **BLOCKED**。
4. 点击线程 → **Monitor & Locks**，查看：
   - 线程 1：持有 `LOCK_A`，等待 `LOCK_B`；
   - 线程 2：持有 `LOCK_B`，等待 `LOCK_A`；
   - 形成 **死锁（Deadlock）**。

#### 4.3.2 阻塞原因分析

`ThreadBlockDemo.java` 中两个线程以 **相反顺序** 获取两把锁，满足死锁四条件（互斥、占有且等待、不可抢占、循环等待）。

#### 4.3.3 修复建议

- 统一锁的获取顺序（始终先 A 后 B）；
- 使用 `tryLock` 超时机制；
- 减少锁粒度或使用并发工具类。

### 4.4 代码运行效能分析

#### 4.4.1 操作步骤

1. Profile 启动 `Main`，参数 `3` 或 `4`。
2. 打开 **CPU Views → Hot Spots**（或 **Call Tree**）。
3. 按 **Self Time** 排序，重点关注：
   - `PerformanceDemo.heavyCalculation`
   - `PerformanceDemo.slowConcat`
   - `StringBuilder` / `String.concat` 相关热点（低效 `+=` 拼接产生大量临时对象）。

#### 4.4.2 性能问题分析

| 方法 | 问题 | 影响 |
|------|------|------|
| `slowConcat` | 循环中使用 `String +=` | 大量临时 String 对象，CPU 与 GC 压力高 |
| `heavyCalculation` | 50 万次 `Math.sqrt` 循环 | CPU 自时间占比高 |

#### 4.4.3 优化建议

- 字符串拼接改用 `StringBuilder`；
- 避免重复计算，可缓存或降低循环次数；
- 对数学运算考虑查表或更高效的算法。

## 六、实验结论

1. **安装配置**：JProfiler 本体与 IDEA 插件配置完成后，可通过 **Profile with JProfiler** 一键 attach，实时查看 JVM  telemetry。
2. **内存泄漏**：通过 Live Memory / Heap Walker 的 Incoming References，可定位到 `LEAK_CACHE` 静态集合持有大量 `LeakItem`，堆内存单调上升，符合泄漏特征。
3. **线程阻塞**：Threads 视图显示 BLOCKED 状态，Monitor & Locks 可确认交叉等待导致的死锁。
4. **效能分析**：Hot Spots 能精确到方法级 CPU 耗时，便于针对性优化 `slowConcat` 与 `heavyCalculation`。
