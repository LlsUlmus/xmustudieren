## 1 实验目的

- 理解 Web 场景下「服务化」与「异步消息」的基本思想，区分 HTTP 接口与长连接推送的差异。  
- 熟悉一种典型的浏览器实时通道：**WebSocket + STOMP**，掌握端点、应用前缀与广播主题的含义。  
- 结合课程要求，探讨**大语言模型**在即时通讯类任务中的用法：例如将「边聊边译」从传统翻译 API 迁移为**可统一建模的文本生成接口**（本实验选用 MiniMax 对话接口完成翻译与情感分析）。  
- 实践前后端分离：后端提供 REST 与 WebSocket 服务，静态页通过 SockJS 连接并完成收发与展示。

## 3 实验内容与步骤

### 3.1 总体架构

- **实时聊天**：浏览器经 SockJS 连接后端 `/ws`，订阅 `/topic/messages`；发送消息到 `/app/chat.send`，服务端处理后**广播**到同一主题，多标签页可同时收到。  
- **边译**：用户发送原文后，服务端调用 MiniMax，将返回结果作为「译文」字段随消息一并推送。  
- **情感与建议**：通过 REST `POST /api/sentiment` 提交文本，模型返回结构化 JSON，前端解析后展示标签、说明与建议回复（可点击填入输入框）。  
- **配置与安全**：`application.yml` 中配置 `minimax.api-key` 等；提交作业时可改用环境变量 `MINIMAX_API_KEY`，避免密钥写入版本库。

### 3.3 运行与验证（简述）

1. 配置 MiniMax 密钥（`application.yml` 或环境变量）。

## 4 思考：用大模型改造聊天软件的思路（不必与本实验实现一一对应）

与传统「翻译 API + 固定语种对」相比，大模型可以**用同一套对话接口**承担多种能力：翻译、摘要、语气改写、合规提示等，减少多厂商、多 SDK 的拼接成本。集成时通常注意：

1. **接口形态**：REST 同步调用适合短文本；长连接场景下可在服务端排队或限流，避免阻塞 WebSocket 线程。
2. **提示词设计**：用 system 指令约束「只输出译文」「只输出 JSON」等，降低胡言乱语与格式错乱。
3. **密钥与配额**：密钥放在服务端或环境变量，前端永不持有；注意 RPM/TPM 等限制，必要时缓存或合并请求。
4. **错误与体验**：网络失败、鉴权失败、内容审核拒答等都应有明确反馈（本实验在 HTTP 与 STOMP 侧均做了基础处理）。
5. **合规**：用户数据是否出境、是否记录日志，需结合课程与平台要求评估。

## 5 实验总结

本次实验在 Spring Boot 上搭建了基于 **WebSocket + STOMP** 的简易群聊通道，并通过 **MiniMax** 大模型接口实现了**边聊天边翻译**以及**情感与回复建议**等扩展能力。过程中加深了对「浏览器长连接 + 服务端广播」与「HTTP 短请求」分工的理解，并体会到提示词与错误处理在实际接入中的重要性。若后续继续扩展，可考虑引入持久化会话、用户鉴权或外置消息队列以支撑更大规模部署，并与本实验的单机内存代理方案对比优劣。
